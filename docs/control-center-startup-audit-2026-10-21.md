## 建议顺序

### 1. 控制脚本并行检查四项服务

`scripts/mes-service-control.ps1` 的 `Get-MesServiceHealth`、启动就绪循环及已运行状态检查按顺序访问 API、前端、LIMS、上位机。服务未准备好时，每轮可能累计四个 2 秒超时；界面已经使用并行请求。

将控制脚本的这四项只读检测并行执行，继续等待同一轮的全部结果，再根据原标准判定是否就绪。保留 LIMS 已连接、上位机已连接且开启自动模式的检查，以及原有失败结果和总等待上限。本机停止状态的分项测量说明，每轮超时检测存在约 6 秒可减少的等待；这不等于完整启动必然缩短 6 秒。

### 2. 前端构建与后端启动重叠执行

`start-dev.ps1` 目前先等待后端 `/health/ready`，随后才执行 `npm run build:production` 和前端服务。前端构建没有请求运行中后端的步骤，可提前与后端启动并行，在开始提供前端服务前继续检查后端就绪。

这可以减少约一次构建耗时的串行等待，同时保留每次构建、原子发布、构建失败重试和历史产物回退。实际收益取决于后端启动耗时与构建耗时的重叠程度。

### 3. 减少首次网卡查询的模块开销

每次启动引导都是新的 PowerShell 进程，因而会重新承担 NetTCPIP 查询的首次开销。可先使用 .NET 枚举；只有一个明确有效的 IPv4／网关候选时走快速路径，多网卡、VPN 或候选不明确时保留原有路由判断。应验证选中的局域网地址与当前行为一致。

## 结论

主要优化空间在启动等待链路。停止服务已经接近 1.7 秒，窗口构建与显示也较快，优先处理串行健康检查、构建与后端启动的串行关系，再处理网卡查询。

以上收益存在重叠，不能直接相加。实施后应在同一台机器复测启动与重启，并确认四项服务仍按原标准就绪，MES、LIMS、上位机三个网页仍统一打开和关闭。

## v2.7.2 已实施及复测

已将四项 HTTP 请求改为并行传输，并复用原有 PowerShell 判定规则；启动、已运行检查和状态查询使用同一套探测。前端现在先构建，再等待后端就绪并提供服务。单一明确物理 IPv4 网关使用 .NET 快速识别，多网关、VPN、多个 IPv4 或网卡信息读取失败时保留原路由路径。

启动减少约 35%，这一对重启测量减少约 37%。随后通过编译后的 v2.7.2 控制中心执行实际重启，服务脚本耗时 10.44 秒，包含浏览器关闭和重新打开的 `RunControl` 总耗时 11.97 秒；界面的成功进度还会停留约 0.65 秒。两次优化后重启的服务耗时为 9.17～10.44 秒，说明收益会随运行条件波动。

实际程序返回三个页面地址，浏览器正常显示；重启后重新打开，关闭系统后专属浏览器可见窗口数为零，四个服务端口均释放，恢复测试前的停止状态。

相关验证通过：PowerShell 启动、停止、构建顺序、单／多网卡、VPN 回退和控制中心 48 项；HTTP 并行探测、就绪规则及桌面部署打包 35 项；前端构建发布、重试与回退 23 项，共 106 项。并行测试以四个独立延迟 HTTP 服务确认请求同时进行，超时不会累计为四倍；失败构建和未就绪后端不会进入前端提供服务步骤。

本次优化作用于开发机脚本，Docker／原生版采用不同的服务控制接口，不能据此宣称它们获得相同启动收益。不是 Windows 系统开机时间测量。
