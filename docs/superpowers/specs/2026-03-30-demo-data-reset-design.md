# 演示数据整库重置设计

## 目标

为当前 MES 演示环境提供一套可重复执行的“整库业务数据重置”能力，彻底清除现有脏数据，并重新生成 20 个全新任务作为统一基线。

这次重置不是增量修补，而是整库业务数据回到干净初始状态。重置后不保留任何旧任务、旧样品、旧实验、旧排程、旧托盘分配和旧冲突记录。

## 重置范围

本次重置清空并重建以下业务数据集合：

- `mes.tasks`
- `mes.samples`
- `mes.experiments`
- `mes.schedules`
- `mes.experiment_trays`
- `mes.experiment_samples`
- `mes.streams`
- `mes.conflicts`

本次重置默认也同步清空 MySQL 中对应业务表的数据，并将 JSON 种子数据重写为新的基线快照，确保 JSON 与 MySQL 不再分叉。

设备定义与系统配置不属于这次重置范围，保持现有实验室/设备基础配置不变。

## 新基线数据规则

### 任务编号与来源

- 固定生成 20 个任务
- 任务编号范围：`SYLU-2026-03-001` 到 `SYLU-2026-03-020`
- `001-010` 固定为 `外部委托`
- `011-020` 固定为 `内部新增`

### 任务初始状态

所有任务统一生成为“全新任务状态”，不预置任何流程进展：

- 任务状态：`待排程`
- 样品状态：`运输中`
- 流转状态：`运输中`
- 接驳状态：未预分装、未接驳、未入库
- 不生成任何已保存托盘、条码、排程、实验开始/完成记录

### 样品与实验生成

- 每个任务固定生成 3 个实验，编码为 `-A / -B / -C`
- 每个任务的 3 个试验类型从系统已有试验类型池中随机抽取，单任务内不重复
- 样品数量随机生成，但统一大于 4
- 对应样品编码按 `TASK-SP-001...` 顺序生成

### 随机性要求

- 试验类型与样品数使用真正随机生成
- 不要求每次重置结果一致
- 只保证结构约束稳定：20 个任务、来源分布固定、每任务 3 个实验、样品数大于 4

## 重置入口设计

新增一个明确的演示数据重置入口，而不是继续依赖手工改 JSON 或手工清库。

入口职责：

1. 生成新的 20 任务完整快照
2. 覆盖写入 `app/data/mes_store.json`
3. 清空 MySQL 当前业务数据
4. 将新快照重新写入 MySQL 业务表
5. 保证重置完成后，`read_all()` 与各业务接口看到的是同一份新基线

这类重置必须是“一次执行、完整收口”的原子化流程，避免出现只清了 MySQL 没改 JSON，或只改了 JSON 没回灌 MySQL 的半完成状态。

## 实现边界

### 推荐实现

采用“生成器 + 重置脚本”两层结构：

- 生成器：负责构造完整业务快照
- 重置脚本：负责清空当前业务数据并写入新快照

这样后续如果要调整任务数量、来源分布、随机池或默认状态，只需要修改生成逻辑，不需要改数据库清理流程。

### 不采用的方案

- 直接手改 `mes_store.json`
  原因：无法保证 MySQL 与 JSON 同步，且不可复用
- 仅依赖 bootstrap 自动回灌
  原因：当前环境已经使用 MySQL 持久化，单靠启动 bootstrap 不足以保证整库重建
- 临时一次性脚本执行后删除
  原因：后续仍有重复重置需求，应该保留稳定入口

## 验证要求

重置完成后需要满足以下事实：

- `mes.tasks` 恰好 20 条
- `mes.samples` 全部属于这 20 个任务，且每任务样品数大于 4
- `mes.experiments` 恰好 60 条，每任务 3 条
- `mes.schedules`、`mes.experiment_trays`、`mes.experiment_samples`、`mes.streams`、`mes.conflicts` 全为空
- `001-010` 来源为 `外部委托`
- `011-020` 来源为 `内部新增`
- 任务、样品、实验在 JSON 与 MySQL 读取结果一致

## 风险与约束

- 该操作会删除当前所有业务演示数据，必须视为破坏性重置
- 随机生成会让每次演示内容不同，适合清脏数据，不适合作为严格快照测试基线
- 如果前端或测试对具体任务名称、样品数、试验类型写死，需要同步改成结构性断言，而不是依赖固定内容
