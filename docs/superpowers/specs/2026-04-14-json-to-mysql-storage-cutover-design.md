# JSON 到 MySQL 业务存储切换设计

## 背景

当前项目的业务数据链路同时依赖三类来源：

- 后端默认存储仍是 `app/data/mes_store.json`
- 后端已存在 `MySQLMesStorageBackend`，但主要作为可切换路径和 JSON 引导后的承接层
- 前端 `storageApi.js`、`tasksApi.js` 仍会把业务数据写入 `localStorage` 作为静默兜底

这带来四个直接问题：

- 业务真实数据源不唯一，问题排查时很难判断一次改动最终落在 JSON、MySQL 还是浏览器本地
- 前端在 API 失败时仍可能展示本地旧数据，容易形成“页面看起来成功、数据库实际上没写进去”的假象
- 演示数据重置和初始化仍会回写 JSON，导致系统长期无法真正脱离文件存储
- 后续从 MySQL 再迁移到达梦时，如果现在不先收口为单一数据库源，下一次迁移会继续背着 JSON 包袱

用户确认的目标是：

- 当前阶段先统一到 MySQL
- 迁移过程以稳定运行为前提，采用可回退的渐进式切换
- 最终去掉 JSON 运行依赖和前端业务 `localStorage` 兜底
- 保留清晰的数据库适配边界，为后续 MySQL -> 达梦迁移做准备
- 现有 MySQL 数据可视为开发/演示数据，可重建，不需要做高风险历史保全迁移

## 目标

- 默认业务持久化后端切换为 MySQL
- 运行期业务读写只以 MySQL 为真相源
- JSON 文件只允许在迁移早期作为一次性导入源，不再参与日常读写
- 前端不再把业务数据写入 `localStorage` 作为兜底
- 演示数据重置、初始化、测试基线逐步改为直接围绕 MySQL 运转
- 保留阶段性开关，任一阶段出现问题可回退到上一阶段
- 设计新的配置和存储边界，使未来接入达梦时替换的是数据库适配层而不是整条业务链路

## 非目标

- 本次不直接切换到达梦
- 本次不全面重写现有 `/api/storage` 为完全领域化 API
- 本次不为生产数据做复杂在线迁移或增量对账机制
- 本次不要求一步删除所有 JSON 相关代码，而是逐阶段收缩其职责范围

## 当前架构梳理

### 后端

- `app/core/storage_backend.py`
  - 定义 `StorageBackend`
  - 提供 `JsonFileStorage`
  - 通过 `get_storage_backend()` 按 `STORAGE_BACKEND` 选择 `json` 或 `mysql`
  - 当前默认值来自 `app/core/config.py`，默认为 `json`
- `app/core/mysql_storage_backend.py`
  - 已实现 `MySQLMesStorageBackend`
  - 负责主要业务集合与 MySQL 关系表之间的映射
  - 仍保留 `_ensure_bootstrapped()`，在空库或缺失集合时从引导存储补数据
- `app/db/mysql_snapshot.py`
  - 提供 `app_storage_snapshot` 快照表
  - 当前主要承接 `mes.conflicts`、`mes.staging_events`、`mes.meta` 这类仍未完全关系化的快照键
- `app/core/demo_data_reset.py`
  - 当前会先重写 JSON，再写入当前后端

### 前端

- `frontend/src/lib/storageApi.js`
  - 会先读写 `localStorage`
  - 远程 API 失败时静默回退本地缓存
- `frontend/src/lib/tasksApi.js`
  - 对 `mes.tasks` 做本地任务缓存
  - 删除、更新、创建后会直接更新本地缓存

### 测试与运行方式

- `tests/core/test_storage_backend.py` 仍将 JSON 路径视为一等存储实现
- `tests/core/test_mysql_storage_backend.py` 覆盖 MySQL 路径
- `README.md` 和 `.env` 运行说明仍未明确把 MySQL 设为默认真相源

## 方案对比

### 方案一：长期双写双读

- JSON、MySQL、前端本地缓存长期并存
- 通过更多同步逻辑维持表面一致

优点：

- 初始风险最低
- 短期回退简单

缺点：

- 系统复杂度最高
- 很难真正完成收口
- 后续切达梦时仍需同时处理 JSON 历史包袱

### 方案二：推荐，分阶段切换并保留开关

- 每一阶段只切一层职责
- 阶段内保留旧开关用于回退
- 阶段完成后缩小旧路径职责范围

优点：

- 符合“稳定优先”的要求
- 可以持续验证并回退
- 最终能把 JSON 和前端本地业务缓存真正移除

缺点：

- 迁移期间配置和测试矩阵会短期复杂一些

### 方案三：一次性切到 MySQL

- 直接把默认后端、初始化、重置、前端缓存、测试全部一次改完

优点：

- 路径最短
- 理论上最终结构最干净

缺点：

- 不符合当前稳定性要求
- 遗漏任一链路都会直接影响运行

## 最终设计

### 核心原则

- MySQL 是当前阶段唯一业务持久化目标
- JSON 在迁移早期只允许做一次性导入，不允许继续承担运行期真相源职责
- 浏览器 `localStorage` 不再保存业务真相，只允许保存非业务类 UI 状态
- 运行逻辑和迁移逻辑必须拆开，避免应用请求链路继续隐式依赖 JSON
- 未来切达梦时，替换点应该是数据库适配层，而不是前端或业务 API 行为

### 目标架构

#### 运行期

- FastAPI 业务请求只读写 MySQL
- `MySQLMesStorageBackend` 成为默认业务存储实现
- `app_storage_snapshot` 继续承载暂未关系化的快照键，直到后续单独关系化
- 健康检查可明确返回当前存储后端类型、MySQL 连通性、是否发生过 bootstrap

#### 迁移期

- 开发环境可通过配置允许空库时从 JSON 一次性导入
- 该导入只在显式允许时发生，且只针对空库或缺失集合
- JSON 文件不再参与日常读写闭环

#### 前端

- 业务数据读取只依赖 API 返回
- 请求失败时页面显式报错或显示空态，不再静默回退本地业务缓存
- 若需要本地缓存，只允许缓存筛选、分页、tab 之类 UI 状态

## 分阶段迁移方案

### 阶段 0：建立迁移护栏

- 为存储后端选择和 bootstrap 增加可观测信息
- 在健康检查中暴露当前存储模式和 MySQL 就绪情况
- 给前端本地业务兜底路径增加显式警告，避免继续“静默成功”
- 补齐 JSON / MySQL 路径的基线测试，固定现状

阶段结果：

- 不改变默认行为
- 能清楚知道系统当前实际走哪条存储路径

### 阶段 1：默认切换到 MySQL

- `STORAGE_BACKEND` 默认值改为 `mysql`
- `get_storage_backend()` 默认返回 `MySQLMesStorageBackend`
- 保留 `json` 显式开关，作为迁移期回退手段
- 空库时允许一次性 JSON bootstrap，但 JSON 不再是默认运行源

阶段结果：

- 业务读写默认落 MySQL
- 应用重启后仍从 MySQL 读取数据

### 阶段 2：移除前端业务 localStorage 兜底

- 去掉 `storageApi.js` 对业务快照的本地持久化兜底
- 去掉 `tasksApi.js` 的任务本地缓存真相源角色
- API 失败时改为显式报错而不是本地伪成功

阶段结果：

- 页面展示与数据库状态保持一致
- 断开 API 时问题能真实暴露

### 阶段 3：把 JSON 降级为一次性迁移工具

- 删除运行期对 `JsonFileStorage(DEFAULT_STORE_PATH)` 的硬依赖
- 新增显式迁移脚本，把 JSON 数据导入 MySQL
- `MYSQL_BOOTSTRAP_FROM_JSON` 改为开发期迁移能力，而不是长期运行期开关

阶段结果：

- 删除 `app/data/mes_store.json` 后，只要 MySQL 已初始化，系统仍可运行

### 阶段 4：初始化、重置、测试全面转向 MySQL

- 演示数据重置直接写 MySQL
- 新增 MySQL 初始化脚本
- 开发环境支持自动建表/自动灌演示数据
- 正式环境只允许脚本初始化
- 测试默认使用 MySQL fixture

阶段结果：

- 开发、测试、演示链路都不再依赖 JSON

### 阶段 5：删除 JSON 运行实现

- 删除 `JsonFileStorage` 的运行职责
- 删除 JSON 模式主路径测试
- 清理文档、配置、脚本中的 JSON 运行说明

阶段结果：

- 项目业务数据链路只剩 MySQL

## 配置设计

建议引入更清晰的配置边界：

- `APP_ENV`
  - `dev | test | prod`
- `STORAGE_BACKEND`
  - 迁移期间保留 `json | mysql`
  - 默认值改为 `mysql`
- `MYSQL_BOOTSTRAP_FROM_JSON`
  - 是否允许空库时从 JSON 一次性导入
- `MYSQL_AUTO_INIT_SCHEMA`
  - 开发环境是否自动补齐 MySQL 结构
- `MYSQL_AUTO_SEED_DEMO`
  - 开发环境是否自动灌演示基线数据

推荐行为矩阵：

- `dev`
  - 默认 `mysql`
  - 允许自动建表
  - 按配置允许自动灌演示数据
- `test`
  - 默认 `mysql`
  - 由测试 fixture 建库/清库
  - 不依赖应用隐式初始化
- `prod`
  - 默认 `mysql`
  - 禁止自动灌演示数据
  - 初始化只允许通过显式脚本执行

## 风险与应对

### 风险一：`/api/storage` 仍是整批快照写入

现有写法更像“前端快照覆盖数据库”，并发和局部修改风险较高。

应对：

- 本次迁移先不重写 API 形态
- 先完成数据源收口
- 后续再单独把高频业务改造成更细粒度领域 API

### 风险二：前端本地兜底掩盖真实失败

用户可能看到页面更新，但数据库没有持久化成功。

应对：

- 在阶段 0 先增加可观测性
- 在阶段 2 彻底移除业务本地兜底

### 风险三：测试受全局单例存储后端污染

`_storage_backend` 是模块级单例，切默认后端后容易串测。

应对：

- 在测试里显式重置后端单例与环境变量
- 增加默认 MySQL 模式下的核心测试

### 风险四：重置脚本继续回写 JSON

会让团队误以为系统已脱离 JSON，实际上维护成本仍在。

应对：

- 在阶段 4 之前显式标注该行为
- 阶段 4 改写为 MySQL-only 重置

## 验收标准

每个阶段都按以下标准验收：

- 功能正确：任务、样品、实验、排程等核心流程行为不回归
- 数据唯一：同一笔业务变更只有一个持久化真相源
- 可观测：能从健康检查、日志、测试中判断实际使用的存储路径
- 可回退：阶段内仍保留上一路径的配置回退能力
- 可迁移：新增设计不会阻碍后续 MySQL -> 达梦切换

最终完成标准：

- 业务运行不再依赖 `app/data/mes_store.json`
- 前端业务数据不再依赖 `localStorage`
- 初始化、重置、测试基线全部直接走 MySQL
- 默认运行模式为 MySQL
- 删除 JSON 文件后，系统在已初始化 MySQL 上可正常运行
- 代码中只保留数据库适配边界，不再保留 JSON 运行实现

## 面向未来达梦迁移的接口约束

- 保持 `StorageBackend` / 存储适配层边界清晰
- 禁止在前端写死 MySQL 特有行为
- 初始化脚本、迁移脚本、重置脚本分离，不和请求处理逻辑耦合
- 所有新增存储健康与配置接口都使用“数据库后端”语义，而不是写死“mysql”字样

这样等未来切到达梦时，需要替换的是数据库适配实现和初始化脚本，而不是再次处理 JSON 与浏览器本地缓存问题。
