# 试验室操作台二级选择设计

## 目标

将现有“盐雾试验室操作台”泛化为“试验室操作台”一级模块，并通过二级实验室选择进入不同实验室的同一套操作台逻辑。每个实验室操作台的功能、界面和流程与盐雾试验室保持一致，只根据当前实验室过滤任务和写入实验室位置。

## 入口与路由

一级模块仍保持一个 `laboratory` 登录模块，一级名称改为“试验室操作台”。二级实验室不新增登录模块、不新增后端权限模块，使用 query 表示当前实验室：

```text
/laboratory?lab=冲击一室
/laboratory?lab=盐雾试验室
```

退出登录弹窗从扁平模块选择改为“一级模块选择 + 实验室二级选择”。只有一级选择“试验室操作台”时显示二级实验室选择。非实验室模块按原逻辑切换；实验室模块先切换登录模块到 `laboratory`，再跳转到带 `lab` query 的 `/laboratory`。

## 实验室清单

二级实验室按用户图三顺序展示：

- 冲击二室
- 冲击一室
- 高低温湿热一室
- 霉菌试验室
- 四综合实验室
- 温度冲击二室
- 温度冲击一室
- 盐雾试验室
- 振动二室
- 振动一室

这些实验室已经存在于前端兜底 `labs.js` 和后端默认主数据 `master_data.py`。本次不新增主数据，只复用现有实验室和试验类型映射。

## 操作台数据口径

操作台按当前实验室名称过滤排程：

```js
schedule.device === currentLabName
```

这样可以正确区分同一试验类型下的多个房间，例如冲击一室/冲击二室、振动一室/振动二室、温度冲击一室/温度冲击二室。`experiment_name` 和 `required_device` 只用于展示、兜底和排程候选，不作为操作台主过滤条件。

页面没有 `lab` query 时，优先读取当前浏览器保存的本机默认实验室；如果没有保存，则默认盐雾试验室。用户从弹窗选择二级实验室后，当前浏览器保存该实验室，便于每台电脑固定展示自己的试验室。

## 配置与状态隔离

当前实验室配置包含：

- `labName`：排程过滤和页面展示使用。
- `labCode`：主数据实验室编码。
- `labId`：MQ payload 使用，优先取主数据 MQTT id，缺失时用实验室编码或名称派生。
- `testTypeName`：展示和兜底使用。

当 `lab` query 改变时，需要重置当前任务选择、托盘选择、扫码反馈、已验证托盘、弹窗状态、运行中实验弹窗恢复定时器、夹具确认倒计时和全文详情弹窗，避免从一个实验室切换到另一个实验室时串台。

## 页面与流程

页面继续复用现有实验室操作台 UI：

- 查看任务
- 任务比对
- 样品安装
- 等待上位机夹具确认
- 确认实验准备就绪
- 运行中实验倒计时
- 实验完成
- 当前任务重置

文案中的盐雾专属内容改为当前实验室或通用“当前实验”。例如“确认后将把当前盐雾实验更新为实验已完成”改为“确认后将把当前实验更新为实验已完成”。

## 测试策略

先补红灯测试，再实现：

- 模块目录和退出弹窗测试：验证一级“试验室操作台”和二级实验室选择。
- App runtime 测试：验证选择实验室后跳转 `/laboratory?lab=实验室名称`，并且登录模块仍为 `laboratory`。
- Laboratory model 测试：验证非盐雾实验室按 `schedule.device` 过滤并选择当前任务。
- Laboratory runtime 测试：验证非盐雾实验室标题、任务清单、MQ `labId`、完成文案和本机默认实验室。
- 聚焦回归测试覆盖原盐雾操作台，保证原有业务逻辑仍可用。
