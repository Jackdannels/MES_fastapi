# 中控总览运行中实验口径设计

## 背景

当前中控总览的“正在运行”卡片按任务状态和排程时间窗统计。这个口径和实际业务不一致：

- 卡片统计的是任务数，不是实验数。
- 只要正式实验室排程落在 `start_at ~ end_at` 时间窗内，任务就会被视为运行中，即使实验尚未由中控正式开启。
- 历史运行态同时存在 `实验中` 和 `实验进行中` 两套文案，前后端口径不稳定。

用户确认的新规则是：只有任一实验室在经过“准备就绪”并由中控下发开启确认实验指令后，到实验实际进入完成态之前，这段时间才属于“正在进行实验”。

## 目标

- 将中控总览卡片标题从“正在运行”改为“正在运行（实验）”。
- 卡片统计值改为“当前处于实验进行中的实验数量”。
- 删除卡片下方“实验中任务”说明。
- 后端将实验运行态统一定义为 `实验进行中`，兼容读取历史 `实验中` 数据，但对外返回和持久化使用统一值。

## 方案对比

### 方案一：按实验实际状态统计

推荐采用。

- 总览卡片直接统计实验列表中状态为 `实验进行中` 的实验数量。
- 后端归一化历史运行态，把 `实验中` 视为兼容输入，在派生状态、读写映射和返回前端时统一成 `实验进行中`。

优点：

- 与实际业务动作一致，中控确认启动后立即进入统计，完成后立即退出。
- 不再依赖排程时间窗，避免计划时间与实际执行不一致时的误判。
- 状态口径集中在后端，前端模型只消费稳定状态。

缺点：

- 需要补齐归一化测试，避免旧数据和旧前端写入值造成回归。

### 方案二：优先实验状态，缺失时回退排程时间窗

- 卡片优先看实验状态，若没有实验状态再按排程窗口兜底。

优点：

- 对历史脏数据更宽容。

缺点：

- 一张卡片同时依赖两套规则，结果难解释。
- 后续排查时很难判断异常统计来自状态源还是排程源。

### 方案三：仅改文案，不改统计

- 页面标题改为“正在运行（实验）”，但继续使用任务级排程时间窗统计。

优点：

- 改动最小。

缺点：

- 文案与实际统计含义继续不一致，不满足需求。

## 最终设计

### 后端状态规则

- 规范运行态常量为 `实验进行中`。
- `实验中` 仅作为兼容输入保留。
- 任何基于样品事件历史推导出的“已启动未完成”实验，都返回 `实验进行中`。
- 任何读取到数据库中 `实验中` 的实验记录，在构造前端返回值时也归一为 `实验进行中`。
- 前端或其他调用方若仍写入 `实验中`，写入数据库前统一归一为 `实验进行中`。

### 中控总览规则

- 卡片标题显示 `正在运行（实验）`。
- 卡片数字统计 `mes.experiments` 中状态为 `实验进行中` 的实验数。
- 卡片不再显示“实验中任务”附注。
- 该卡片不再依赖任务状态，也不再依赖正式排程的时间窗。

### 兼容性

- 旧状态 `实验中` 会继续被识别为运行态，避免历史数据瞬间失效。
- 任务状态是否继续显示为 `实验中` 不作为本次 KPI 计算依据；总览卡片只基于实验状态。
- 其他依赖运行态集合的逻辑可以继续暂时接受两种输入，但统一输出应逐步收敛到 `实验进行中`。

## 影响范围

- 后端：
  - `app/core/mysql_storage_backend.py`
  - 相关单元测试 `tests/core/test_mysql_storage_backend.py`
- 前端中控总览：
  - `frontend/src/modules/dashboard/model.js`
  - `frontend/src/modules/dashboard/page.vue`
  - `frontend/src/modules/dashboard/model.test.js`
  - `frontend/src/modules/dashboard/page.runtime.test.js`
- 前端实验启动流程：
  - 检查 `frontend/src/modules/process/useProcessLabs.js` 是否仍持久化 `实验中`，必要时一并归一。

## 测试策略

- 后端单元测试覆盖：
  - 历史样品事件推导运行态时返回 `实验进行中`
  - 旧输入 `实验中` 写入或读取时被归一为 `实验进行中`
- 前端单元测试覆盖：
  - 总览卡片只统计运行中的实验，不统计运行中的任务
  - 未来排程但未启动的实验不计入卡片
  - 页面标题改为 `正在运行（实验）`，卡片附注被移除
