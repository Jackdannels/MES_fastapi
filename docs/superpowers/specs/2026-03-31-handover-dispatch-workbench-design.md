# 接驳区工作台任务总览与样品出库设计

## 背景

当前接驳区系统使用 `TransferWorkbench` 统一承接任务总览、托盘分装、条码打印和确认入库。页面顶部只有 `退出登录` 按钮，工作流仍停留在“到样确认”阶段，缺少接驳区将托盘送往暂存间或实验室的首段派送入口。

现有数据模型已经具备以下基础能力：

- 托盘和样品可记录 `送至暂存间 / 已到达暂存间 / 送至实验室 / 已到达实验室` 等状态
- `experiment_trays` 可表达托盘与实验的多对多关系
- `schedules` 可表达实验对应的具体实验室和时间
- 样品历史 `history` 已用于追溯接驳区、暂存间和实验过程中的状态变化

本轮需求是在接驳区工作台内新增一个并列的 `样品出库` 视图，并保持“到样确认”仍然对应当前总览与托盘分装界面。

## 目标

本轮实现以下能力：

1. 在接驳区工作台顶部的 `退出登录` 左侧新增 `任务总览` 和 `样品出库` 两个按钮
2. `任务总览` 按钮继续显示当前接驳区总览和任务内托盘分装界面
3. `样品出库` 视图支持扫码或手工输入托盘编号
4. 扫码后展示该托盘对应的暂存间和实验室候选
5. 若托盘关联多个实验，显示对应多个实验室，并高亮排程时间最近的实验室
6. 允许托盘从接驳区先标记为 `送至暂存间` 或 `送至实验室`
7. 同步更新该托盘下样品和托盘的状态、位置与历史

本轮明确不做：

- 不在接驳区完成 `已到达暂存间 / 已到达实验室` 的二次确认
- 不改造暂存间系统或实验室页面的到达确认流程
- 不接真实扫码枪驱动，仍由输入框承接扫码结果
- 不支持批量多托盘一次出库

## 页面结构

### 顶部切换

接驳区工作台顶部操作区调整为：

- `任务总览`
- `样品出库`
- `退出登录`

其中：

- `任务总览` 对应当前 `TransferWorkbench` 的总览和托盘分装流程
- `样品出库` 对应新的扫码派送视图
- 两个工作视图保留在同一工作台内，不新增子路由

### 内部组织方式

保持 `TransferWorkbench` 作为工作台外壳，但将其内部拆分为两个面板：

1. `OverviewPanel`
   - 负责当前已有的任务列表、任务详情、托盘分装、保存托盘、打印条码、确认入库
2. `DispatchPanel`
   - 负责样品出库扫码、候选去向展示、派送确认和结果反馈

这样可以复用现有登录、退出、模式配置与接驳区样式，同时避免继续在单一大文件里堆叠更多流程。

## 样品出库交互

### 扫码流程

`样品出库` 视图包含：

1. 托盘扫码输入框
2. 扫码提示文案
3. 托盘结果卡
4. 去向候选区
5. 成功或失败反馈区

建议提示文案：

`请扫描托盘条码，系统将自动匹配目标实验室或暂存间。`

### 校验规则

扫码后先校验托盘是否允许从接驳区发出。允许条件：

- 托盘属于已完成接驳区托盘分装和确认到货的任务
- 当前托盘状态仍位于接驳区发出前阶段
- 托盘尚未进入 `送至暂存间 / 已到达暂存间 / 送至实验室 / 已到达实验室` 等后续阶段

不允许时返回明确提示，例如：

- `该托盘尚未确认入库，不能出库`
- `该托盘已送往目标位置，请勿重复操作`
- `未找到托盘，请检查扫码内容`

### 结果展示

扫码成功后展示：

- 托盘编号
- 所属任务编号
- 托盘当前状态
- 托盘内样品数量
- 托盘关联实验
- 候选去向列表

### 去向列表

去向列表采用固定排序：

1. 最左侧固定展示 `暂存间`
2. 其后展示该托盘关联实验对应的实验室候选

候选实验室不按试验类型硬编码，而是按托盘关联实验和排程表动态解析。

### 点击后的动作

点击候选后只执行“发出”动作，不做“到达确认”：

- 选择 `暂存间`：托盘和样品状态改为 `送至暂存间`
- 选择实验室：托盘和样品状态改为 `送至实验室`

成功后保留当前托盘结果区，并显示：

- `托盘 XXX 已标记为送至暂存间`
- `托盘 XXX 已标记为送至 四综合实验室`

页面保持可继续扫描下一托盘。

## 目标实验室判定规则

### 数据来源

托盘候选实验来源按以下优先关系生成：

1. 通过 `experiment_trays` 找到当前 `tray_code` 关联的 `experiment_code`
2. 通过 `experiments` 取回实验名称
3. 通过 `schedules` 按 `task_code + experiment_code` 找到正式排程
4. 若存在正式排程，则以排程中的 `device` 作为目标实验室，`start_at` 作为时间比较依据

### 多实验托盘

若托盘同时绑定两个实验，则并列展示两个实验室候选；若两个实验都尚未排程，则展示两个 `待排程` 候选。

### 高亮规则

- `暂存间` 永远可选，但不参与“最近时间”比较
- 只有存在明确 `start_at` 的实验室候选才参与时间排序
- 开始时间最近的实验室高亮，并显示 `优先送达`
- 若多个实验室时间完全相同，则都不高亮
- 若所有实验都没有正式排程，则都不高亮，仅显示 `待排程`

### 未排程实验

若实验尚未绑定正式实验室，不猜测具体实验室名，候选文案显示：

`<实验名>（待排程）`

该候选不高亮，也不应伪装成实际实验室。

## 状态写回规则

### 发往暂存间

- 托盘状态：`送至暂存间`
- 样品状态：`送至暂存间`
- 样品 `flow_status`：`送至暂存间`
- 样品 `location`：`恒温恒湿间（暂存间）`
- 样品历史新增一条：
  - `action`: `送至暂存间`
  - `detail`: 记录托盘编号

### 发往实验室

- 托盘状态：`送至实验室`
- 样品状态：`送至实验室`
- 样品 `flow_status`：`送至实验室`
- 样品 `location`：目标实验室名
- 样品历史新增一条：
  - `action`: `送至实验室`
  - `detail`: 记录托盘编号和目标实验室

### 模型说明

本系统已有 `status` 和 `location` 并存的流转模型。本轮保持该模型：

- `location` 表示当前指向的目标地点
- `status` / `flow_status` 表示仍处于“送往途中”

因此在目的地完成二次确认前，样品和托盘都停留在 `送至...` 状态。

## 接口设计

### 查询托盘出库候选

新增：

`GET /api/transfer-area/trays/{tray_code}/dispatch`

返回内容：

- 托盘基本信息
- 所属任务
- 托盘当前状态
- 托盘样品数
- 托盘关联实验
- 候选去向列表
- 候选是否高亮、是否可选、关联排程时间

### 执行托盘出库

新增：

`POST /api/transfer-area/trays/{tray_code}/dispatch`

请求体：

- `targetType`: `staging` 或 `lab`
- `targetName`: 暂存间名称或实验室名称
- `experimentCode`: 可选；当托盘绑定多个实验且选择实验室时用于标记本次派送语义

返回内容：

- 更新后的托盘信息
- 更新后的状态文案
- 受影响样品数量
- 操作结果提示

## 错误处理

需要显式处理以下场景：

- 托盘不存在
- 托盘尚未入库确认，不允许出库
- 托盘已经进入后续流转状态，不允许重复派送
- 扫码到的托盘没有任何可用样品
- 目标实验室与该托盘无关联
- 候选实验尚未排程但用户强行选择实验室

错误文案应直接说明原因，不返回模糊提示。

## 测试与验收

### 后端

需要覆盖：

1. 扫码托盘后返回 `暂存间 + 实验室候选`
2. 单托盘多实验时返回多个实验室，并正确高亮最近时间
3. 未排程实验只显示 `待排程`，不高亮
4. 发往暂存间后，托盘和样品都变成 `送至暂存间`
5. 发往实验室后，托盘和样品都变成 `送至实验室`
6. 已经发出的托盘不能重复发出

### 前端

需要覆盖：

1. 顶部新增 `任务总览` 和 `样品出库` 按钮，位置在 `退出登录` 左侧
2. 点击 `任务总览` 仍显示当前总览和托盘分装流程
3. 点击 `样品出库` 切换到扫码派送视图
4. 扫码后展示候选去向
5. 多实验时最近时间的实验室显示高亮和 `优先送达`
6. 点击候选后刷新状态和成功提示

## 备注

本轮只完成接驳区的“发出”动作。暂存间系统和实验室页面中的“已到达”二次确认留到后续独立任务中完成。
