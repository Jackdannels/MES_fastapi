# 多实验任务排程与接驳区托盘分配设计

## 背景

当前系统默认一条任务只对应一个实验类型：

- `task.code` 是排程主键
- `task.test_type` 同时承担任务实验类型、设备需求、页面展示等职责
- 接驳区按 `task_code` 聚合样品与托盘，默认一个任务只做一套托盘分配

新的业务要求是：

1. 一个任务编号下可以包含多个实验编号
2. 排程要按 `任务编号 + 实验编号` 进行，而不是按任务整体排程
3. 同一份样品记录可以同时参与多个实验
4. 接驳区先按任务完成一次托盘分装，再针对每个实验从现有托盘中选择参与该实验的托盘
5. 托盘在实验模式下只允许选择，不允许改变托盘内样品摆放
6. 条码内容仍只使用托盘编号，但打印标签上需要展示该托盘参与的实验标签

这意味着系统需要从“任务即实验”的模型升级为“任务包含多个实验”的两层模型。

## 目标

本轮设计目标：

1. 引入独立的 `实验编号` 概念，并将其作为排程最小单位
2. 保持任务、样品、托盘三者现有主关系不被拆散
3. 接驳区改成“任务托盘编辑模式 + 实验托盘选择模式”
4. 托盘结构修改采用前端草稿缓存，统一保存后再允许打印条码
5. 数据库和 JSON 快照同时支持多实验任务模型

## 非目标

本轮明确不做：

- 不把同一份样品拆成多条实验子样记录
- 不为每个实验再复制一套独立托盘结构
- 不修改条码编码内容，条码值仍然只使用托盘编号
- 不把一个任务强行拆成多个伪任务编号

## 核心模型

### 任务、实验、样品、托盘关系

- `task`
  - 仍然表示一次委托/送样任务
  - 负责汇总该任务下的样品、实验与托盘
- `experiment`
  - 新增任务下的实验实体
  - 是排程和实验执行的最小业务单位
- `sample`
  - 仍然只属于一个任务
  - 不直接复制为多条实验记录
- `tray`
  - 仍然只属于一个任务
  - 托盘内样品摆放先按任务统一分装
- `experiment_tray`
  - 表示某实验使用了该任务下哪些托盘
  - 样品参与哪些实验，由“实验选中的托盘包含哪些样品”推导得到

这次不单独维护 `sample -> experiment` 持久化关系，避免它与 `experiment -> tray -> sample` 同时存在而产生漂移。页面需要展示样品参与实验时，可以在运行时从托盘关联反推。

### 编号规则

- 任务编号保持原格式，例如：`SZH-2026-006`
- 实验编号采用“任务编号 + 后缀”规则，例如：
  - `SZH-2026-006-A`
  - `SZH-2026-006-B`
  - `SZH-2026-006-C`
- 界面短标签可显示为：
  - `A实验`
  - `B实验`
  - `C实验`

存储与接口统一使用完整 `experiment_code`，页面可派生短标签显示。

## 存储模型

### JSON 快照

新增两个集合：

- `mes.experiments`
  - 任务下实验主数据
- `mes.experiment_trays`
  - 实验与托盘的关联数据

保留现有：

- `mes.tasks`
- `mes.schedules`
- `mes.samples`

建议字段：

`mes.experiments`

- `id`
- `task_code`
- `experiment_code`
- `experiment_name`
- `required_device`
- `priority`
- `planned_hours`
- `status`
- `created_at`
- `updated_at`

`mes.experiment_trays`

- `id`
- `task_code`
- `experiment_code`
- `tray_code`
- `created_at`
- `updated_at`

`mes.schedules`

- 保留现有字段
- 新增 `experiment_code`

`mes.tasks`

- 保留现有字段
- 新增汇总字段：
  - `experiment_count`
  - `experiment_codes`

### MySQL 表结构

#### 新增 `biz_experiment`

建议字段：

- `experiment_id` bigint primary key
- `experiment_no` varchar unique
- `task_id` bigint nullable
- `task_no` varchar not null
- `experiment_name` varchar not null
- `required_device` varchar
- `priority` int or varchar
- `planned_hours` decimal
- `experiment_status` varchar
- `created_at` datetime
- `updated_at` datetime
- 索引：
  - `idx_biz_experiment_task_no (task_no)`
  - `uk_biz_experiment_no (experiment_no)`

#### 新增 `biz_experiment_tray`

建议字段：

- `id` bigint primary key
- `experiment_no` varchar not null
- `task_no` varchar not null
- `tray_no` varchar not null
- `created_at` datetime
- `updated_at` datetime
- 唯一约束：
  - `(experiment_no, tray_no)`
- 索引：
  - `idx_biz_experiment_tray_task_no (task_no)`
  - `idx_biz_experiment_tray_tray_no (tray_no)`

#### 扩展 `biz_schedule`

新增字段：

- `experiment_no` varchar

新排程数据必须写入 `task_no + experiment_no`。历史旧数据若没有实验号，可在读写层按兼容逻辑视为“默认唯一实验”，但新功能默认按显式实验处理。

#### 扩展 `biz_task`

建议新增：

- `experiment_count` int

该字段用于总览页快速展示，不作为唯一事实来源；真实实验数据来自 `biz_experiment`。

## 页面与交互

### 任务定义页

任务创建/编辑需要支持为一个任务维护多个实验：

- 任务基本信息仍保留
- 任务编辑器中新增“实验列表”区域
- 可新增/删除实验条目
- 每个实验维护：
  - 实验编号
  - 实验名称
  - 设备需求
  - 优先级
  - 计划时长

任务页显示的任务类型不能再只依赖单个 `task.test_type`。总览卡片应新增“实验数量”和实验摘要，避免误导为单实验任务。

### 排程页

排程对象从“任务”升级为“实验”：

- 待排程列表按实验行展示
- 每行至少显示：
  - 任务编号
  - 实验编号
  - 实验名称
  - 设备需求
  - 当前状态
  - 已选托盘数
- 拖入时间槽、手动创建、编辑、删除排程时都针对 `experiment_code`
- `schedule.task_code` 继续保留用于归属与任务级汇总

任务级状态由该任务下实验排程综合推导，而不是再假设一个任务只有一个实验状态。

### 接驳区

接驳区任务详情改成“双层模式”：

- `任务托盘`
  - 编辑任务级托盘结构
- `A实验 / B实验 / C实验 ...`
  - 选择该实验使用哪些托盘

#### 任务托盘模式

允许：

- 拖动样品
- 交换样品
- 新增托盘
- 删除托盘
- 调整统一上限

不在这个模式下立即写库，而是写入当前任务的前端草稿。

#### 实验模式

只允许：

- 查看已有托盘
- 选择或取消当前实验使用的托盘

不允许：

- 拖动样品
- 交换样品
- 新增托盘
- 删除托盘
- 修改统一上限

实验模式消费的仍是任务模式生成的托盘草稿，不单独维护新的托盘布局。

#### 托盘标签

每个托盘卡片需要展示它已经被哪些实验选中，例如：

- `A实验`
- `A实验 B实验`
- `A实验 B实验 +2`

当前实验模式下，如果该托盘已经被当前实验选择，需要有高亮反馈；如果被其他实验使用，仅显示标签，不做禁用。

### 草稿与保存

接驳区改为前端缓存草稿后统一保存：

- 任务托盘编辑只改前端草稿
- 实验选托盘只改前端草稿
- 所有实验都完成托盘选择后，才允许点击统一的 `保存托盘`

保存时一次性提交两类数据：

1. 任务级托盘结构
2. 所有实验的托盘选择结果

后端应在一次提交中事务化写入：

- 样品与托盘关系
- 实验与托盘关系

### 草稿重置规则

若任务托盘结构发生真实变化，例如：

- 新增托盘
- 删除托盘
- 样品跨托盘移动
- 样品交换
- 调整统一上限导致重排

则当前任务下所有实验草稿选择立即清空，并清空托盘上的实验标签，提示：

`任务托盘已变更，原实验安排已重置，请重新分配各实验托盘。`

该重置发生在前端草稿层；只有统一保存后，新的任务托盘结构与实验托盘关系才正式持久化。

## 打印规则

- 条形码编码内容仍然只使用托盘编号
- 未保存草稿前不可打印条形码
- 保存成功后才允许打印

打印标签建议展示：

- 主体：托盘编号
- 辅助标签：该托盘参与的实验标签，例如 `A实验 B实验`

也就是说：

- 机器扫描内容不变
- 人工识别信息增加实验标签

## 后端接口原则

### 排程

排程相关读写接口都需要接受并返回 `experiment_code`。任务维度接口若继续存在，需要补充任务下实验列表，避免前端只能拿到任务号却无法定位实验。

### 接驳区

接驳区接口需要补充：

- 任务详情中的实验列表
- 每个实验当前已选托盘
- 任务草稿统一保存接口

统一保存接口建议单次提交：

- `trayLimit`
- `trays`
- `experimentTrays`

后端提交成功后返回完整工作区视图，供前端刷新成“已保存正式态”。

## 测试与验证目标

### 数据模型

1. 一个任务可包含多个实验
2. 一个实验可独立排程
3. 同一托盘可被多个实验同时引用
4. 样品参与哪些实验可由实验托盘关系正确推导

### 排程

1. 同一任务下多个实验可排到不同时间和不同设备
2. 排程编辑、删除、冲突检测都基于 `experiment_code`
3. 任务状态可从实验排程综合推导

### 接驳区

1. 任务托盘模式允许编辑托盘结构
2. 实验模式仅允许选择托盘
3. 任务托盘草稿变化会清空实验托盘草稿
4. 所有实验分配完成前不能统一保存
5. 保存成功后才能打印条码
6. 托盘标签正确显示对应实验

### 数据库

1. `biz_experiment` 可正确写入和回读
2. `biz_experiment_tray` 可正确写入和回读
3. `biz_schedule.experiment_no` 可正确持久化
4. JSON 与 MySQL 两种存储模式下前端视图保持一致
